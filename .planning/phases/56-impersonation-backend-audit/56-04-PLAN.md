    In `subscription.guard.ts`, add an impersonation bypass check in the `canActivate` method. After the existing `@SkipSubscriptionCheck()` reflector check and before the subscription status check, add:

    ```typescript
    const request = context.switchToHttp().getRequest();
    if (request.impersonator) {
      return true;
    }
    ```

    This check must go AFTER the `!user` null check (so we know request.user is populated) but BEFORE the subscription status lookup. The logic: if a support user is impersonating a customer, the support user has already been authenticated and authorized by JwtAuthGuard. The impersonation session itself is the authorization — subscription gating should not block the support user from viewing the customer's data.

    Do NOT use `hasPermission(request.impersonator, "bypass_subscription")` — the impersonator field only exists on impersonation requests, and its presence alone is sufficient proof that the request is authorized (the JwtAuthGuard already validated the impersonation token and hydrated the impersonator).

    In the test file `subscription.guard.spec.ts`, add two tests:

    1. "should allow request when request.impersonator is set (impersonation session)" — mock request with a valid user AND impersonator field set, assert canActivate returns true without checking subscription status.

    2. "should still check subscription when request.impersonator is not set" — existing behavior unchanged for normal (non-impersonated) requests.

    Pattern for accessing request in guard tests: use `createMock<ExecutionContext>()` or the existing test mock pattern in the spec file. Set `request.impersonator` to a mock IUserDto object.

    Gap reason: SubscriptionGuard.canActivate throws ForbiddenError at line 46 when target user (customer) has no subscription during impersonation. The guard does not recognize impersonation context.

  <action>
    In `impersonation-creator.service.ts`, modify the concurrent session check. Currently the code:
    1. Calls `findBySupportUserId(authUser.id)` to get all audit entries
    2. Filters for entries with `status === ImpersonationStatus.ACTIVE`
    3. Throws ForbiddenError if any ACTIVE session exists

    Change this behavior: instead of throwing when an ACTIVE session exists, auto-terminate the stale session by calling `this.auditRepository.markEnded(activeSession.id, DateTime.utc())` for each ACTIVE session found, then proceed with creating the new session normally.

    The implementation should:
    - Find all sessions for the support user via `findBySupportUserId()`
    - Filter for `status === ImpersonationStatus.ACTIVE`
    - For each active session, call `markEnded(session.id, DateTime.utc())` to terminate it
    - Log a warning when auto-terminating: `this.logger.warn("Auto-terminating stale impersonation session", { sessionId: activeSession.id, supportUserId: authUser.id })`
    - Then proceed with the normal session creation flow (create audit entry, sign JWT, return token)

    This handles the browser-refresh scenario: the old session gets terminated in the audit log (preserving the audit trail), and a new session is created. The old JWT is already effectively dead because the JwtAuthGuard checks `session.status !== ImpersonationStatus.ACTIVE` before granting access.

    In the test file `impersonation-creator.service.spec.ts`, update the existing concurrent session test:
    - Remove or update the test that asserts ForbiddenError is thrown for concurrent sessions
    - Add test: "should auto-terminate existing ACTIVE session and create new session" — mock `findBySupportUserId` to return an entry with ACTIVE status, assert `markEnded` is called with the old session ID, assert a new session is still created successfully
    - Add test: "should not call markEnded when no ACTIVE sessions exist" — mock returns only ENDED/EXPIRED entries, assert `markEnded` is NOT called, assert new session created normally

    Gap reason: After browser refresh, frontend loses the impersonation token but backend session remains ACTIVE. Concurrent session prevention blocks new session start, leaving the support user unable to resume or restart impersonation.
